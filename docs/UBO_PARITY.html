What changed on 2026-08-01. Everything adblock-rust parsed and we were throwing away is now used. That was the cheap half of the gap and it is closed:

  • All 24 network options the crate accepts now do something — $csp, $ping and $websocket were the last three. $ping then went further than the crate strictly offers: a sendBeacon() call is matched by asking a second time, which the 58 $ping-only rules in your lists needed. See 2.1.

The one correction to the earlier version of this page: procedural cosmetic rules do not need the page-to-proxy channel, so they did not need extension/ first. The rules for a page are known when the page is served, so they are embedded in it. Only the question "what matches a class name that appeared later?" needs a channel back, and that is the one thing still Chromium-only.

Two labels on this page were also corrected, because both overstated a gap. $all does block popup navigations — the crate's mask includes the document type — so only the empty window survives, not the ad. And generic hiding is limited by a browser mixed-content rule, not by anything adblock-rust withholds.

What is left is the half that needs machinery we do not have: an HTML filter, a response-body rewriter, a side table for the options the crate refuses, and popups.

These all come from one place: request_type in adblock/classify.rs reads sec-fetch-dest, falling back to x-requested-with, then to accept. Naming a request is a filtering decision, so adblock does it, not the proxy that hands the request over.

$websocket and $ping arrive with no usable sec-fetch-dest, so each is read from the header that does name it: Upgrade: websocket for the first, Content-Type: text/ping for the second.

That second header only covers hyperlink auditing (<a ping>). The other half of $ping is navigator.sendBeacon(), and it is worth being exact about why it is hard: a beacon is a POST with Sec-Fetch-Mode: no-cors and Sec-Fetch-Dest: empty, which is byte-for-byte what fetch(url, {mode: "no-cors", method: "POST"}) sends. There is no header that separates them. uBO is not cleverer here; it is simply handed a resource type by the browser.

Labelling every such POST a ping would be a bad trade — the lists hold 971 $xhr rules against 70 $ping ones, so it would lose far more than it gained. Instead adblock matches the request as the fetch it appears to be, and if nothing matched, asks its own engine once more as a ping. Both sets of rules apply, the extra lookup only happens on requests already shaped like a beacon, and a second look can only ever add a block.

Why this was worth doing rather than documenting: of the 70 $ping rules in your lists, 12 also name $xhr or another type and would have caught a mislabelled beacon anyway — but 58 name $ping and nothing else. Those 58 are the rules that exist precisely because the endpoint is a beacon, and they were the ones missing it. The one behavioural difference from uBO: a genuine no-cors fetch POST can now also be matched by a $ping rule. Since those rules name beacon endpoints by URL, that is the intent.

$all is the row most likely to be misread, so: the blocking works. adblock-rust compiles $all to FROM_ALL_TYPES = FROM_NETWORK_TYPES | FROM_DOCUMENT (filters/network.rs:139–142) — and that includes the document type. A popup is a window navigating to a URL, and that navigation reaches us as a document request, so an $all rule blocks it like any other page load. Nothing gets through.

What is missing is only the window. uBO sees the tab being created and stops it from opening; we let it open and then serve it nothing, so the user gets a blank window instead of no window. That is a worse experience, not a filtering gap, which is why the tag reads window still opens rather than "no popups". The crate has no popup concept to borrow either: RequestType has no such variant, $popup is rejected outright, and the crate's own source carries the note // TODO Could also include popup.

$webrtc never touches HTTP — a WebRTC connection is negotiated by the page and goes out over UDP. A proxy cannot see it. uBO blocks it by neutering RTCPeerConnection in the page, which is what the nowebrtc scriptlet does, and that scriptlet does work here. So the option is unsupported but the effect is covered.

2.6 Getting past the closed option table without a parser

The table is closed, but the crate still gives us enough to work around it, so none of these rows require writing a filter parser.

  • adblock::lists::parse_filter (src/lists.rs:393) and FilterSet::add_filter (:247) are public and return a typed error for one rule. We can see exactly which rules are rejected, and why, at load time — that is how the 4,157 figure on this page was produced.
  • src/adblock/mod.rs:444 already builds FilterSet::new(true), so BlockerResult.filter comes back carrying the text of the rule that matched. attribution() at mod.rs:381 already uses it.

That is enough for the obvious approach: at load, strip the option the crate refuses, give the remainder to the engine, and record the extra condition in a table keyed by the rule text. At match time the engine names the rule, so checking the extra condition is a lookup, not a second matching engine. What needs writing is one small check per option — is the method GET, is the host in the $denyallow set — not a parser.

What the crate does with them: parses each into a CosmeticFilterOperator or CosmeticFilterAction, serialises the pair to JSON, and returns it on UrlSpecificResources.procedural_actions. What we now do with them: cosmetic_css() keeps calling as_css() and emits everything that reduces to a stylesheet, and procedural_injection() takes the rest — the ones as_css() answers None for — and embeds that JSON in src/adblock/injected/procedural_runtime.js. The proxy injects the finished script without reading it, so nothing is applied twice and no rule is dropped.

The evaluator walks each rule's chain against the live DOM: the first entry is a plain CSS selector, and each operator after it narrows the set (:has-text, :matches-css) or moves it (:upward, :xpath). Then the action runs — hide by default, or :style(), :remove(), :remove-attr(), :remove-class(). A debounced MutationObserver re-runs it for content that arrives later. Every action reads the page's current state before changing anything, so a pass with nothing to do makes no edit at all: that is what keeps its own edits from waking it forever, and it also means a rule the page has undone gets applied again.

Two things it is worth being honest about. Injecting it strips the page's CSP, like any inline script of ours. And an :upward() or :remove() rule now deletes real nodes, so a bad rule breaks a page more visibly than a bad hide rule does.

4. What needs a live DOM, and what that actually blocks

This was billed as the single biggest parity item. It turned out to be two separate problems that were being counted as one, and only the smaller of them is still open — which is why this section has been rewritten rather than ticked off.

4.1 The rule

A filter can be decided in the proxy if everything it needs is in the bytes going past: the URL, the request headers, the response headers, the response body. A filter needs a live DOM if it depends on something that only exists after the browser has parsed the page and run its JavaScript.

Depends onWhere it livesDecidable in the proxy?
The URL, the request method, headersThe requestYes
The response body as servedThe responseYes
A CSS selector with no procedural partHanded to the browser as a stylesheetYes — the browser evaluates it for us
The text inside an elementOnly after parsingNo
The computed style of an elementOnly after layoutNo
An element that JavaScript createdOnly after scripts runNo
Deleting a node, or an attribute, or a classAn action, not a selectionNo — CSS can hide, it cannot delete

That last row is worth dwelling on. :remove() is not a matching problem, it is a capability problem. CSS can make something invisible. It cannot take it out of the document. Some anti-adblock scripts check whether their element is still present, not whether it is visible, so hiding is not always as good as removing.

4.2 The 19 things that need a live DOM

  • 16 cosmetic operators — everything in the table above marked live DOM. The 10 of them adblock-rust parses now run in the injected evaluator.
  • Generic cosmetic filtering on content that JavaScript adds after load. This is the one that still needs a channel back to the proxy — see 4.3.
  • The #?# rule family (working) and #$?# (the crate rejects it)
  • ##^responseheader() is not one of these — it is a header, pure proxy work

4.3 Two live-DOM problems, only one of which needs a channel

This is the distinction the earlier version of this page got wrong, and it decides what is blocked and what is not.

Applying a rule to the live DOM needs no channel. Which procedural rules a page gets is decided by its hostname, which the proxy knows as it serves the page. So the rules go into the page with the page, and src/adblock/injected/procedural_runtime.js evaluates them there. Nothing is asked of the proxy, nothing crosses an origin, and it works in every browser.

Asking which generic rule matches a name that appeared later does. There are hundreds of thousands of generic rules; they cannot all be sent, so the page has to ask. src/adblock/injected/cosmetic_runtime.js watches the page with a MutationObserver, collects new class and id names, and asks what matches.

That second one used to fail in Safari and Firefox.

[blocked] The page at https://www.youtube.com/... requested insecure content
from http://127.0.0.1:8081/api/cosmetic. This content was blocked.

The runtime is injected into the page, so its request carried the page's origin. An https:// page making a plain http:// request is mixed content. Chromium allowed it because it treats 127.0.0.1 as trustworthy. WebKit and Gecko do not. cosmetic_runtime.js swallows a failed lookup in an empty catch, which is why it went unnoticed.

Fixed. The page now asks its own address — https://that-site.example/__abx/cosmetic — and Adblock recognises the path and answers it as the request passes through, instead of letting it go upstream. Same origin, so no mixed content and no CORS, and it works from whichever machine is browsing rather than only the one the proxy runs on. src/adblock/routes.rs holds the reserved prefix and the table of endpoints under it; matching happens before any filter rule is consulted, so no list can shadow one and none of these questions ever reaches the site. The detector weights for the picture blur travel the same way.

This is why extension/ exists — and the generic lookup is no longer one of the reasons. A background script's request leaves the extension's own origin, so mixed content does not apply, and it is still the only route to $popup.

The procedural evaluator never waited for any of this, because it never needed to ask anything.

Why $popup is the hard one

Measured against the lists: 3,127 rules, which is 81% of every network rule the engine rejects and 75% of everything dropped for any reason. It is the one place a proxy is genuinely worse placed than a browser extension.

A popup rule means "block this URL, but only when it is opening a new window". uBO knows that because the browser tells it — it sees the tab being created and which page created it. At the HTTP layer a popup and a clicked link are the same thing: a document request with Sec-Fetch-Mode: navigate. No header distinguishes them.

  1. Treat $popup as $document. Most of these rules target domains that exist only to serve popup ads, so blocking them on any navigation is usually right. "Usually" means some deliberate clicks would break, with no obvious cause. Worth knowing: this is already what happens for $all rules, which include the document type — so the approach is in use, just not yet extended to $popup itself.
  2. Do it in the extension. A content script sees window.open; a background script sees tab creation. Correct, and only works where the extension is installed.

7. Two honest caveats about "100%"

Some of the gap is already covered twice. 17 of the 48 $replace rules target YouTube, stripping "adPlacements" out of the player response. uBO also ships scriptlet versions of exactly those edits — trusted-replace-fetch-response, json-prune-fetch-response — and those scriptlets do run here. uBO does it in both places deliberately, as belt and braces. Adding $replace gives you the belt you are missing; the braces are already holding.

Parity with which uBO? Three of the big gaps — $replace, HTML filtering, $cname — only exist in uBO on Firefox. uBO on Chrome never had them, because Chrome has no webRequest.filterResponseData and no DNS API for extensions. uBOL has none of the three either. Measured against uBOL we are now ahead on almost everything: procedural cosmetic used to be the one place we were behind it, and that closed on 2026-08-01. What is left against uBOL is generic hiding of JavaScript-added content outside Chromium — see item 5. Measured against uBO on Firefox, the table above is the distance.

The vendor/ubol-safari/ checkout this page originally cited is no longer in the repository, so the uBO side was re-read from uBO's own source upstream (gorhill/uBlock, src/js/static-filtering-parser.js). Every line number below was confirmed against that file on 2026-08-01; the crate references were confirmed against the adblock 0.9.8 source in the Cargo registry.

  • uBO's supported options: nodeTypeFromOptionName at static-filtering-parser.js:223–292. 50 canonical options, plus 17 synonyms and one empty "unknown" entry.
  • uBO's cosmetic operators: proceduralOperatorTokens at line 4193 of the same file. 24 entries, 19 canonical once aliases are folded in.
  • uBO's rule families: the separator regex /(#@?(?:\$\?|\$|%|\?)?#).{1,2}/ at line 803, plus the dispatch in parseExtPattern() at line 2365.
  • What we support: the match table at adblock-0.9.8/src/filters/network.rs:391–466. Anything not in it hits UnrecognisedOption and the whole rule is discarded by add_filter_list, silently. 25 accepted spellings, one of which ($tag) is the crate's own and not a uBO option — so 24 of uBO's 50. Cosmetic separators at filters/cosmetic.rs:355–400; the CSS conversion at cosmetic_filter_cache.rs:403. The $redirect= priority suffix is split off in blocker.rs:289–318.
  • What the crate parses, and where it lands now: the procedural operators are canonicalised at filters/cosmetic.rs:886–936 — 9 accepted, 13 rejected in the same match. Three of those 13 (remove, remove-attr, remove-class) are rejected only as selectors; they are handled as actions instead. The four actions are CosmeticFilterAction at filters/cosmetic.rs:51–75. Both reach us through UrlSpecificResources.procedural_actions, and AdBlocker::procedural_injection (src/adblock/mod.rs:354) hands the evaluator everything as_css() cannot express. Stand-in file types are MimeType at src/resources/mod.rs:199–226; the converter emits all of them.
  • Which rules are dropped, and why, per rule: parse_filter at src/lists.rs:393 and FilterSet::add_filter at :247, both public, both returning FilterParseError. Every non-comment line in data/blocklists/ was run through parse_filter and the error variants tallied — that is where 4,157 and its breakdown come from, and it is the crate's own verdict rather than a reimplementation of its tables.
  • Per-option use counts: a separate pass using uBO's option names. Two details matter and were wrong before: the option separator is found by scanning right to left for a $ whose next token is a real option name (a pattern can contain $ itself), and a value beginning with / is a regex that runs to its closing slash, so commas inside $replace= do not split the option list. The per-option totals from this pass agree with the crate's own 3,881 exactly.
  • The percentages: counted off the tables in this document, one row per rule type. Covered is the rows marked full or part over all rows; of the crate is the same over only the rows where the adblock-rust column says yes. §2.4 has 16 rows for 14 options because the two uBO synonyms are listed separately.
  • Rule counts: every non-comment line in the 15 files in data/blocklists/ — 1,470,512 as of 2026-08-01. All 15 are loaded — DiskStore::load reads every .txt in the directory, there is no enabled flag.
  • Scriptlet and stand-in coverage: names from every ##+js(...) and $redirect= token, matched against the names and aliases in data/scriptlets/scriptlets.json, then compared against the file list of src/web_accessible_resources/ in uBO upstream (50 files) and the alias map in src/js/redirect-resources.js.
